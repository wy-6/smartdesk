## 1. Day 29：RAG 到底在做什么

### 1.1 一句话

**RAG = 先检索，再把检索到的资料塞进 Prompt，最后让模型基于资料回答。**

```
用户提问
   ↓
① 检索（Embedding → 向量比对 → Top-K 片段）   ← 这一步不经过大模型
   ↓
② 组装（片段编号 + 内容 + 问题）
   ↓
③ 生成（模型只依据资料回答，并标注引用编号）
   ↓
④ 校验（引用编号必须真实存在）
```

### 1.2 为什么要有"独立检索流程"

第 5 周的验收门槛写得很死：

> 不接受只有一个聊天接口、没有独立检索流程、没有来源引用的实现。

原因只有一个：**出了问题你分不清是检索的锅还是生成的锅。**

- 模型答错了 → 是"资料没召回来"（检索问题）还是"召回了但没用好"（生成问题）？
- 两者的修法完全不同：前者调切片/Top-K/Embedding，后者调 Prompt。

所以本项目有**三个独立接口**：`/documents`（索引）、`/search`（检索）、`/ask`（问答）。
`/search` 不调模型，返回的就是检索原始结果：片段内容、来源文件、分块 ID、**相似度分数**。

### 1.3 向量检索 ≠ 关键词搜索

| | 关键词搜索（LIKE / 全文索引） | 向量检索 |
|---|---|---|
| 匹配什么 | 字面（词形） | 语义（向量夹角） |
| "报销期限" vs "报销时限" | ❌ 匹配不上 | ✅ 能匹配（真实语义模型） |
| 实现 | B+ 树倒排 | Embedding → 余弦相似度 |
| 弱点 | 精确、同义失效 | 精确匹配反而可能失效（"30 天" vs "30日"） |

**面试可讲**：真实系统常用**混合检索**（向量 + 关键词 BM25），
向量负责"意思相近"，关键词负责"精确命中"（错误码、金额、编号）。
本项目的 mock 嵌入是词元哈希，只能覆盖关键词那一半 —— 这是它明确的局限。

## 2. Day 30：解析、分块与元数据

### 2.1 为什么要切

一份制度 5000 字，整段塞进 Prompt 有三个问题：
1. **贵**：每个问题都要把整份文档的 token 付一遍
2. **慢**：上下文越长，模型响应越慢
3. **糊**：一个块里混了 10 个主题，向量被平均，谁都不像

### 2.2 切得太小 / 太大的后果（本周最重要的知识点）

| | 切太小 | 切太大 |
|---|---|---|
| 后果 | 一个完整意思被劈成两半，模型看到残句只能猜 | 多个主题混在一个块，向量被"平均" |
| 现象 | 召回率上去了，**答案却不对** | 看起来召回了，**但不是最相关的那块** |
| 评测表现 | hit@k 高、hit@1 低 | hit@k 低、hit@1 也未必高 |

第 5 周的评测数据直接验证了这一点（`docs/week5-eval-result.md`）：

| 配置 | chunk-size | overlap | top-k | hit@1 | hit@k |
|---|---|---|---|---|---|
| A（默认） | 400 | 80 | 5 | 83.3% | 90.0% |
| B（大切片） | 800 | 0 | 3 | 83.3% | 90.0% |
| C（小切片） | 150 | 30 | 5 | 76.7% | **96.7%** |

**读出来的结论**：小切片**召回更高**（96.7% vs 90%），但**精度略降**（76.7% vs 83.3%）——
小块的向量更"纯"（只讲一件事），所以更容易进 Top-5；但 Top-1 位置上，
大块里往往也混着答案，词面重合更多。**这就是召回与精度的经典权衡**。

### 2.3 重叠（overlap）解决什么

答案正好落在切割线上 → 被劈成两半 → 两半都不完整 → 召回失败。
重叠让下一片的起点回退 N 个字符，保证跨界句至少有一片是完整的。

本项目的 `Chunker`：
1. 优先在句末标点（`。！？；\n`）处断开
2. 找不到句末标点才在分句标点（`，、：）处断
3. 都没有才硬切
4. 尾巴不足 `min-chunk-size` → 并入上一片，不产生碎片
5. 每片记录 `charStart` / `charEnd`，能还原原文位置

### 2.4 元数据：页码、文件 ID、分块编号

计划书要求"保存文件 ID、文档名称、分块编号和页码（如可获取）"，对应实现：

| 元数据 | 落在哪 | 用途 |
|---|---|---|
| 文件 ID | `kb_document.id` | 引用溯源 |
| 文档名称 | `kb_document.title` | 引用里显示"来源：XXX" |
| 分块编号 | `kb_chunk.chunk_index` | 定位到第几片 |
| 页码 | `kb_chunk.page_no` | PDF 专属，翻到第几页 |

PDF 逐页抽取（`PDFTextStripper.setStartPage/setEndPage`），所以页码是**真的页码**。
TXT/Markdown 没有页码概念，`page_no` 为 null。

## 3. Day 31：Embedding 与向量存储

### 3.1 选型：为什么自己实现 MySQL 版 VectorStore

| 方案 | 优点 | 否决理由 |
|---|---|---|
| `SimpleVectorStore`（Spring AI 官方内存版） | 零依赖 | **过滤在内存里做**；本项目硬约定是"过滤必须下沉到 SQL" |
| Milvus / Qdrant / pgvector | 工业级 | 本机 Docker 不可用（wsl 被封），起不来 |
| **自研 MySQL 版 `VectorStore`** | 过滤在 SQL、离线可跑、可用 Spring AI 抽象 | —— |

最终方案：**实现 Spring AI 官方的 `VectorStore` 接口**。
好处是业务代码依赖的是 Spring AI 的抽象，将来换 pgvector 只需要换实现类，检索代码一行不改。

### 3.2 Embedding 模型 vs 聊天模型

| | 聊天模型 | Embedding 模型 |
|---|---|---|
| 输入输出 | 文本 → 文本 | 文本 → 一维向量（256 维 float32） |
| 能力 | 生成、推理 | 只有"编码"，不能生成 |
| 协议 | `/chat/completions` | `/embeddings` |
| 计费 | 按输出 token 贵 | 按 token 便宜，但调用量巨大 |

本项目两个都是 Spring AI 官方接口：
- `EmbeddingModel` → `MockEmbeddingModel` / `OpenAiCompatibleEmbeddingModel`
- `ChatModel` → `MockChatModel` / `OpenAiCompatibleChatModel`

**注意**：DeepSeek **没有** embedding 接口，只有聊天。所以配置里聊天和嵌入是**两套**：
`smartdesk.ai.*`（聊天）与 `smartdesk.rag.embedding.*`（嵌入）。
用百炼可以同一家搞定（`text-embedding-v3`）。

### 3.3 mock 嵌入的实现与局限

`MockEmbeddingModel` 做的是**带符号哈希**：
1. 分词：英文按单词、中文按**二元组**（bigram）
2. 每个词元哈希到固定维度的一个桶，带正负号（碰撞时正负抵消，避免相似度虚高）
3. 次线性词频（`1 + log(tf)`）—— 同一个词出现 10 次不该有 10 倍权重
4. L2 归一化

它**不理解语义**："报销期限" vs "报销时限" 这种同义不同词匹配不上。
但它**确定性**、离线、免费，所以适合做 CI 和可复现的评测。

### 3.4 向量怎么存

`embedding` 存 **BLOB**（float32 小端字节序），不是 JSON 文本：
- 256 维 float32 = 1KB；存 JSON 要 6KB 左右
- 读回来直接 `ByteBuffer` 解析成 `float[]`，没有字符串解析开销

同时存 `embedding_dim`：换过 embedding 模型后，旧向量维度对不上，
检索时直接跳过并打 WARN，而不是当 0 分混进结果里。

## 4. Day 32：检索的四个旋钮

### 4.1 Top-K

召回多少个片段。**Top-K 一定有 K 个结果**，哪怕一个都不相关 ——
所以必须配阈值。

### 4.2 相似度阈值

低于 `similarity-threshold`（默认 0.05）的不返回。
**宁可说"没查到"，也不要给模型喂一堆噪音** —— 噪音会诱导编造。

### 4.3 元数据过滤（owner_id）

本项目的**隔离红线**：

```java
// MySqlKnowledgeVectorStore
if (ownerId == null) {
    throw new IllegalArgumentException("检索必须带 owner_id 过滤条件（这是隔离的硬约束，不允许绕过）");
}
```

SQL 层面长这样：

```sql
SELECT ... FROM kb_chunk WHERE owner_id = ? LIMIT 5000
```

**过滤在 SQL 里完成，不是查出来在内存里筛。** 这条有专门的单元测试守着
（`MySqlKnowledgeVectorStoreTest` 第一条断言就是"没有 owner 过滤的检索必须被拒绝"）。

另外 `delete(List<String> idList)` 被**故意禁用**（抛 `UnsupportedOperationException`）：
按裸 id 删除没有归属校验，是越权入口。删除只能走
`KnowledgeService.delete(ownerId, documentId)`，先校验归属再删。

### 4.4 单文档限流

如果用户上传了 10 份内容高度相似的制度，Top-K 可能全被同一份文档占满 ——
看起来"召回很多"，实际只有一个信息源。所以每个文档最多贡献
`max-chunks-per-document`（默认 50）个片段。

### 4.5 检索结果要能看到分数

响应示例：

```json
{
  "query": "报销期限是多久",
  "topK": 5,
  "threshold": 0.05,
  "count": 2,
  "hits": [{
    "chunkId": 12, "documentId": 3, "documentTitle": "公司报销制度",
    "chunkIndex": 0, "pageNo": null,
    "content": "...", "score": 0.42,
    "charStart": 0, "charEnd": 380
  }]
}
```

**没有分数就没法评估召回质量** —— 这是第 5 周的核心验收点之一。

## 5. Day 33：Prompt、引用与拒答

### 5.1 四条规则

```
1. 只使用【资料】中的事实。不要用资料以外的知识补充、推测或举例。
2. 每条结论后面标注来源编号，格式如 [1]、[2]。编号对应资料条目前的编号。
3. 如果【资料】里没有回答问题所需的信息，必须回答"根据现有资料无法确认这个问题。"，
   不允许猜测、不允许说"一般来说""通常情况下"。
4. 如果【资料】之间互相矛盾，直接指出矛盾点，并说明分别出自哪几条资料。
```

第 3 条最容易被忽略、后果最严重：**模型天生倾向于"尽力回答"，
而在企业知识库场景里，"尽力"就等于编造。**

### 5.2 引用由检索结果生成，不由模型生成

这是本模块最重要的设计决策：

- **我们的** `citations` 列表来自真实检索到的片段，编号与资料区块严格对齐
- **模型的** `[1]` 只是"声称"用了第 1 条资料
- 如果模型编了 `[99]`，我们能立刻发现（99 不在 citations 里）→ `unsupportedMarkers`

反过来，如果让模型自己编引用，它会编得很像 —— 格式对、编号连续，
但对应的文本根本不存在，用户点进去才发现是空的。

### 5.3 检索不到就不调模型

```java
if (hits.isEmpty()) {
    return new AskResponse(question, REFUSAL_ANSWER, true, List.of(), 0, List.of(), null);
}
```

既省钱（一次模型调用不便宜）又杜绝幻觉。而且**拒答时也返回 citations**
（此时为空）—— 用户需要知道"系统查了，没查到"，而不是"系统坏了"。

### 5.4 资料与问题的顺序

**问题放在资料后面**。长上下文里"最后的问题"权重更高，放后面模型不容易漏看。

## 6. Day 34：检索评测

### 6.1 评测集

`src/test/resources/rag/eval-dataset.json`：10 份制度文档 + 30 道问题，
每题带一个**期望关键词**（只要召回片段里出现它就算命中）。

### 6.2 两个指标分开看

| 指标 | 衡量 | 说明 |
|---|---|---|
| hit@1 / hit@k | 检索 | 召回的片段里有没有期望关键词 |
| 引用正确率 | 生成 | 模型引用的来源片段里是不是真的有答案 |
| 引用错误数 | 幻觉 | 模型引用了不存在的编号（**必须恒为 0**） |

分开看才能区分"没检索到"和"检索到了但没用好"。

### 6.3 评测报告进版本库

`docs/week5-eval-result.md` 由 `RagEvaluationTest` 自动生成。
**为什么要进 git**：改了切片策略，下次跑测试报告会变，
`git diff` 就能看出"这次改动让检索变好还是变坏" —— 结论需要被 review。

## 7. Day 35：工程细节

### 7.1 重复导入

内容 SHA-256 哈希 → 命中已有文档就**直接返回，不重新向量化**
（重新 embedding 要花钱，而且会产生两份一样的索引）。
不同用户导入相同内容**不算重复**（哈希查询带 owner 条件）。

### 7.2 异常输入

| 输入 | 结果 |
|---|---|
| 空文件 / 空白正文 | 400 `KNOWLEDGE_DOCUMENT_EMPTY` |
| 不支持的扩展名 | 400 `KNOWLEDGE_UNSUPPORTED_FORMAT`（明确列出支持哪些） |
| 扫描件 PDF（无文本层） | 400 + 提示"可能是扫描件，需要先做 OCR" |
| 超长文档 | 400 `KNOWLEDGE_DOCUMENT_TOO_LARGE` |

### 7.3 索引流程

```
原始字节 → 解析（按页）→ 内容哈希（重复判定）→ 切片 → 向量化 → 写 kb_chunk → 更新切片数
```

**文档与切片在同一个事务里**：不能出现"文档建好了但切片只有一半"的中间态 ——
那样用户检索时会得到残缺答案，而且完全看不出哪里出了问题。

## 8. 本周真坑（11 个）

1. **Spring AI 的 `Document.Builder` 不接受 null 元数据值** —— `page_no` 为 null 时
   `metadata(k, null)` 直接抛 `IllegalArgumentException`。必须在 null 时跳过。
2. **MyBatis-Plus 单元测试缺 lambda 缓存** —— 纯单元测试里没 Spring 上下文，
   `LambdaQueryWrapper` 解析 `KnowledgeChunk::getOwnerId` 会报
   "can not find lambda cache"。要手动 `TableInfoHelper.initTableInfo(...)`。
3. **一个类有多个构造器时 Spring 不知道选哪个** —— 报 "No default constructor found"，
   而且**只在集成测试里出现**（单元测试用 new，不走容器）。必须加 `@Autowired`。
4. **MySQL 客户端读 UTF-8 脚本要显式指定字符集** —— 否则中文字符串默认值报
   "Invalid default value"，而且是执行到一半才失败，前面 DROP 已经执行了。
5. **测试库 schema 手工执行 = 迟早忘** —— 现在 `application-test.yml` 里配了
   `spring.sql.init.mode=always`，每次测试上下文启动自动重建，测试与建表脚本永远同步。
6. **mock 嵌入是词法模型，不是不相关就零分** —— "公司食堂几点开饭"里的"公司"
   和制度里的"公司"撞上了，相似度过阈值。写拒答用例时查询必须**零词元重叠**。
7. **短文档 + 大 chunk = 向量被平均** —— 评测里失败的 3 道题全部来自"整份文档装进一个 chunk"。
8. **引用正确率不能用截断摘要判定** —— `snippet()` 只截 200 字，答案常在第 200 字之后，
   用摘要判会误判。要用完整片段内容判定。
9. **mock 永远取第一片的第一句 = 答非所问** —— 一个切片里往往含多个小节
   （年假制度 + 报销制度 + 考勤制度），问"住宿费上限"却答"一、年假制度"。
   "回答里带 [1]"这类断言发现不了这种 bug —— 必须有一条专门断言
   "回答内容与问题相关"的测试。修法：在最高分资料内部按词元重叠选句。
10. **只测"原题召回率"会高估检索效果** —— 用户不会照着文档的措辞提问。
    本周给 30 道题各配了一个**同义改写**，结果：原题 hit@5 90.0%，
    改写后只剩 63.3%，**损失 26.7 个百分点**。这条差距完全来自嵌入模型，
    不测就以为检索做得很好。
11. **切片越小，泛化能力越差** —— 小切片配置原题召回最高（96.7%），
    但改写后召回反而最低（56.7%）。切片小 = 向量更聚焦 = 更依赖精确词面匹配。
    **只看原题召回率会选错配置**，必须把"原题"和"改写"分开测。

## 9. 面试题（10 道）

1. RAG 的完整流程是什么？哪一步不经过大模型？
2. 为什么文档要切分？切得太小、太大的后果分别是什么？
3. 重叠（overlap）解决什么问题？设多大合适？
4. Embedding 模型和聊天模型有什么区别？为什么计费方式不同？
5. Top-K 是什么？为什么检索结果不一定相关？阈值怎么定？
6. 怎么判断是"检索问题"还是"生成问题"？
7. 如何避免不同用户检索到彼此的私有文档？为什么过滤要下沉到 SQL？
8. 如何让引用与真实检索片段对应，而不是让模型自己编引用？
9. 检索召回率低，你会按什么顺序排查？
10. 为什么你的向量存储自己实现，而不是用现成的？

<details><summary>参考答案要点</summary>

1. 解析 → 切片 → 向量化 → 存储；查询时嵌入 → 过滤 → 相似度排序 → Top-K → 组装 Prompt → 生成 → 校验引用。**检索环节不经过大模型**。
2. 成本、上下文污染、向量被平均。太小=残句，太大=多主题混合。
3. 解决"答案正好落在切割线上"。经验值 10%~20% 的块大小，且必须小于块大小（否则死循环）。
4. 一个生成文本，一个只做文本→向量。embedding 调用量巨大（每片文档都要一次），所以更便宜但量更大。
5. Top-K 召回数量。一定有 K 个结果，不管相不相关。阈值用来剔除噪音，宁可拒答。
6. 先看检索结果（`/search`）里有没有答案：有→生成问题；没有→检索问题。
7. owner_id 来自 JWT，写进每条切片的冗余列，检索 SQL 带 `WHERE owner_id=?`；并且**没有过滤条件的检索直接拒绝执行**。
8. 引用列表由检索结果生成、编号与资料一一对应；模型只允许引用已有编号；越界编号记为 `unsupportedMarkers`。
9. 顺序：① 看召回的片段对不对（切片策略）→ ② 看相似度分布（阈值/Embedding）→ ③ 看 Top-K（召回 vs 噪音）→ ④ 换真实语义嵌入。
10. 现成的要么过滤在内存（隔离不落地），要么需要 Docker 起不了；自己实现还能兼容 Spring AI 的 `VectorStore` 抽象，换库只改实现类。
